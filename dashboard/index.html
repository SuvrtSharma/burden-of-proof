Burden of Proof evidence

What this page is

An AI agent built a small ledger API: parties, dated bills, payments, advances (money paid before it is owed) and reversals. Then it proposed six changes to make the API faster. Agents state claims like "this is safe" or "this is faster" with confidence, and some of those claims are wrong. This project checks every claim with a tool before anyone believes it. This page shows every result of one run, including what failed.

Each claim is split in two. Meaning: does the system still give the right answers and keep its rules? That can be checked, with mathematical proof and by comparing the real code with a model. Speed: is it faster? That can only be measured, and measurements are noisy. Meaning is judged first, without any timing. A change that breaks a rule is rejected, however fast it is.

How a claim is judged

  1. The claimThe agent states what it changes and which guarantees it gives up. Each claim is a record in claims/.
  2. Guarantee checkThe checker opens a live database with the change applied and reads its real settings. If a guarantee is lost and the agent didn't declare it, the claim is rejected.
  3. Lean proofA claim that gives up a guarantee needs a proof, in Lean 4, that the ledger's rules still hold. Lean is a proof assistant: a program that checks every step of a mathematical proof.
  4. ConformanceThe real code and a runnable copy of the spec process the same random operations, and they must give the same answer every time. A disagreement is shrunk to the shortest sequence that still fails.
  5. Only then, timingAccepted claims are timed in interleaved rounds, against a baseline that is measured again in every round.

What this run shows

  • The proofs hold. — Lean claims about the ledger passed every check, including two independent proof checkers ("kernels"). They were checked against the spec the owner reviewed and locked.
  • The checks can fail. — deliberate breakages of the checker were each caught by its tests. In the checker container, — tests passed and — failed.
  • Wrong claims were caught. — optimisation claims were accepted. Capping the scan of open bills was refuted by a Lean proof and by conformance, and nothing proved it safe. WAL with synchronous=NORMAL gave perfect answers but quietly gave up durability, so it was rejected too.
  • The speed-up is real, within limits. The accepted changes together ran at — the baseline's median throughput. Some accepted changes, on their own, were inside this machine's noise. That is reported as "no result", not as "slower" (Speed tab).
  • The limits. The spec is a model. Comparing the code with it tests samples of behaviour and doesn't prove the SQL. Everything ran on one laptop, in one WSL2 VM, against a ledger the agent wrote. The measurements expire on the date in the header.

Words used on this page

Claim
A statement an agent makes about the code that can be checked or measured, such as "adding this index is safe and faster".
Guarantee
Something the platform provides that the ledger's rules rely on. For example, a committed payment survives a power cut (durable commit).
Spec
The ledger's rules written in Lean: what a bill, a payment and a settlement are, and what must always hold. The owner reviews and locks it.
Spec lock
A file of SHA-256 fingerprints of the spec. If anyone, the agent included, changes one character, every proof is rejected until the owner re-approves the spec.
Kernel
The small core of a proof checker that every proof is finally checked by. Two independent kernels are used here: Lean's own (leanchecker) and con-leche.
Kernel replay
Re-checking the compiled proofs with a kernel, from scratch. It catches proofs that were added with checking switched off, which a normal build doesn't.
Axiom
A fact a proof assumes without proof. Only Lean's three standard ones are allowed. Any other axiom could assume the claim itself.
Vacuity witness
Proof that a claim's assumptions can actually be met. "Every unicorn is green" is true only because there are no unicorns. The witness rules out that kind of empty truth.
Refutation
A proof that a claim is false.
Conformance
Running the real code and the compiled spec on the same random operations and comparing every answer.
Shrinker
Cuts a failing operation sequence down to the shortest one that still fails, so a person can read it.
Mutation / bites
A mutation deliberately breaks one check. A test "bites" if it then fails. A check whose tests still pass when it is broken protects nothing.
WAL
Write-ahead logging, a SQLite journal mode that writes changes to a log first. It is usually faster for this kind of load.
synchronous
SQLite's setting for how often it waits for the disk to confirm a write (fsync). Lower settings are faster, and some of them lose recent commits on a power cut.
fsync
Asking the operating system to put written data on the disk itself, not only in memory.
Nagle's algorithm
A TCP setting that holds back small packets. Combined with delayed acknowledgements, it added about 40 ms to each response in the first run (finding F-016). TCP_NODELAY turns it off.
req/s
Successful requests completed per second of measured time, from the load generator's view.
p50, p95, p99
Latency percentiles: half, 95% and 99% of requests finished within this time. They are computed by nearest rank over every successful request, with no sampling.
Round
One pass that runs every configuration once, in a shuffled order. Several rounds show how much results drift on their own.
Baseline
The ledger before any optimisation, with a durable database setting.

What the speed numbers support

A configuration counts as faster only if its slowest round beat the baseline's fastest round, and as slower only in the opposite case. Anything in between is inside the noise. This machine's disk stalls writes for seconds at a time (findings F-018, F-026), so the noise is large.

What each claim says

      
Open a claim to see its exact Lean statement, quoted from Spec/Ledger.lean at the lines shown. The proof had to prove exactly that statement. "Invariant" claims hold in every state the ledger can reach from any sequence of operations. "Property" claims are about one function or one step. The spec's terms: run ops is the ledger state after the operations ops; outstanding is what a bill still owes; advance is what is left of a payment; matchUp pairs open bills with advances, oldest bill first.

      

    


    

      
What each check guards against

      

        
1. Spec lock
The spec is the one the owner approved. Without it, an agent could prove a claim by quietly weakening the rule.

        
2. Build
The spec and the proofs compile with the pinned Lean version.

        
3. Shape
The statement is a proposition defined in the spec, built only from the spec, and the proof's type is exactly that statement. This stops a proof of something else, or of a copy of the rule defined outside the spec.

        
4. Axioms
The proof assumes nothing beyond Lean's three standard axioms. An extra axiom, or sorry, would assume the result.

        
5. No foreign code
Nothing marked unsafe, implemented_by or extern. These let compiled code differ from what was proved.

        
6. Vacuity witness
A separate proof that the claim's assumptions can be met, so the claim isn't true only because nothing satisfies them. A refutation (a proof of "false") doesn't need one.

        
7. Kernel replay
Lean's own kernel re-checks every compiled proof. This is the check that caught a forged theorem built with kernel checking switched off. That forgery passed the build and #print axioms.

        
8. Second kernel
An independent kernel (con-leche) checks the same proofs, so one kernel bug isn't enough to fool the pipeline.

How each number was made

      
Every figure on this page starts as a file that a command wrote during the run. The page reads those files when it opens. It either shows a value as recorded, or computes it in a calculation whose code is listed in Sources. Nothing is typed in by hand, apart from the findings log, which is written by people and says so below. The commands are the ones in docs/RUNBOOK.md, run by the owner from a clean checkout.

      
Timing ran in two containers on separate CPUs: the API server on CPUs 0–3, the load generator on CPUs 4–7. Each configuration got a fresh server and its own database volume, seeded with the same data. The load generator ran a fixed mix of operations from several threads for a fixed time and recorded every request: its operation, status, start time and latency. All figures come from those records.

      
Meaning ran in the checker container, with no timing involved. For each claim: the database settings were read from a live database with the change applied, the Lean evidence went through the same pipeline as the Proofs tab, and the real store and the compiled spec processed the same seeded random operation sequences (their counts and seed are in Meaning verdicts).
